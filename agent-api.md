# Research workspace API

Production: `http://127.0.0.1:4173`. Test: `http://127.0.0.1:4175`.
Start with `GET /api/v1/schema`. Responses are JSON. If configured, send
`Authorization: Bearer $LABBOOK_AGENT_TOKEN` (the server environment variable).
Never send an OpenAI key as the agent token.

Each collection supports GET (list), GET `/:id`, POST (create), PATCH `/:id`
(merge fields) and DELETE `/:id`. List endpoints accept exact field filters,
for example `/api/v1/experiments?noteId=NOTE_ID`. Writes validate references,
hierarchy cycles, training status, numeric metrics and column mappings.
Deletion rejects dangling references; unlink dependants first.

GET returns ETag and X-Labbook-Revision headers. Send the revision in If-Match
when a write depends on a previous read. A stale revision returns 409; fetch,
inspect and retry deliberately. PATCH applies to fresh server state, preserving
other collections. POST with an existing `externalId` returns that entity
without overwriting it. Use PATCH for updates.

## Collections and fields

IDs are generated by POST. Use returned IDs in dependent records.

* `notes`: `title`, `folder` (existing folder ID, usually `inbox`), `content`
  (editor HTML), `parentNoteId` (optional parent note), `boardIds` (array).
  Research streams are ordinary notes created from a template, not a separate
  entity. Use normal internal links `/notes/ID`.
* `boards`: `name`, `columns` (unique nonempty string array), optional `noteId`.
  To link a board to a page, PATCH the page's `boardIds` as well.
* `tasks`: `text`, `board`, `col` (source board column), `type`
  (`epic`, `task`, `subtask`), optional `parentId`, `noteId`, `tags`, `tag`,
  `description`. Epics cannot have parents; tasks may belong to epics;
  subtasks may belong to tasks or epics. Parents cannot be subtasks.
* `repositories`: `name`, `url` (HTTP/S), `defaultBranch`, optional `noteId`.
* `branches`: `name`, `repoId`, optional `parentId` (branch in same repo),
  `noteId`, `commit`, `prNumber`, `prUrl`, `prStatus`
  (`none`, `open`, `closed`, `merged`), `merged` (boolean).
* `experiments`: `name`, `status` (`planned`, `queued`, `training`, `trained`,
  `failed`, `cancelled`), `metrics` (numeric values, or values typed by a column schema),
  optional `config`, `noteId`, `taskId`, `repoId`, `branchId`, `machine`,
  `cluster`, `runUrl`. Branch must belong to the specified repository.
* `boardViews`: `name`, `boardIds`, optional `columnMap`:
  `{"BOARD_ID":{"Reading":"In progress","Validating":"Review"}}`.
  This is a saved query over source boards; it does not copy tasks.
* `tableSchemas`: one schema per `collection`, with an ordered `columns` array.
  Each column has stable `id`, `key`, `label`, `source` (`metrics`, `config`,
  `properties`), `type`, and optional `objective` (`none`, `max`, `min`), `unit`,
  `precision` (0–10), `min`, `max`, `description`, `hidden`, and `options`.
  Types: `continuous`, `integer`, `categorical`, `ordinal`, `boolean`, `text`,
  `date` (YYYY-MM-DD), `url` (HTTP/S), and `json` (structured value).
  Categorical and ordinal columns require unique string `options`. Ordinal
  options run from lowest to highest, defining comparison order. Higher/lower
  preference applies to numeric and ordinal columns. Missing values remain
  last when sorting. A missing measurement is absent/null, never fabricated 0.
  Numeric bounds are optional. Renaming a label or hiding a column preserves
  stored data; changing a type or option set must remain compatible with all
  existing values. Keys and sources identify stored values and should stay
  stable. Configuration fields remain in `config`; metrics remain in `metrics`.
  The editor and validation engine are reusable for other collections, such
  as `tasks` with custom values stored in `properties`.

Example column schema:

```json
{
  "collection": "experiments",
  "columns": [
    {"id":"validation-loss","key":"loss","label":"Validation loss","source":"metrics","type":"continuous","objective":"min","precision":4},
    {"id":"review","key":"review","label":"Review quality","source":"metrics","type":"ordinal","options":["low","medium","high"],"objective":"max"},
    {"id":"precision","key":"precision","label":"Precision","source":"config","type":"categorical","options":["fp16","bf16"],"objective":"none"}
  ]
}
```

Example experiment body:

```json
{
  "externalId": "run-2026-11-09-a",
  "name": "Temporal attention ablation",
  "status": "training",
  "metrics": {},
  "config": {"temporal_attention": false, "seed": 42},
  "machine": "gpu-node-03",
  "cluster": "research"
}
```

Only report measured metrics and known job/PR states. There is no automatic
Git synchronization or training orchestration. After external API updates,
reload open browser windows before editing: revision checks reject stale
browser saves instead of overwriting agent updates.

## Clickable diagrams in notes

Use `+ → HTML / SVG diagram` in the editor. Agent-authored content can contain
normal `<a href="/notes/NOTE_ID">` or SVG `<a href="/boards/BOARD_ID">` links.
External HTTP/S and mailto links work; `#section` targets stay inside the
diagram. Scripts, event handlers and forms are disabled.

To create a diagram through the API, append this block to a note's existing
content (read it first and send If-Match):

```js
const block = '<div contenteditable="false" class="architecture-block" ' +
  'data-architecture="' + encodeURIComponent(svgOrHtml) + '"></div><p><br></p>';
```

Other live editor blocks use canonical empty containers:

```html
<div contenteditable="false" class="hub-embed" data-research-block="experiments" data-source-id="NOTE_ID"></div>
<div contenteditable="false" class="hub-embed" data-research-block="branches" data-source-id="REPO_ID"></div>
<div contenteditable="false" class="hub-embed" data-research-block="board" data-source-id="BOARD_ID"></div>
```

Keep existing note content and paper embeds when adding blocks. Draft saves
do not create manual versions. API updates should set `draft: true`; manual
versions remain snapshots created with Save version in the editor.
# Multi-user visibility

Every shareable entity may include `visibility`: `private`, `workspace`, or
`shared`, plus an optional `ownerId` and `sharedWith` array. Use the `users`
collection for local workspace identities and the `shares` collection for
explicit `view` or `edit` permissions. Existing records without these fields
remain workspace-visible for backwards compatibility.

Example:

```json
POST /api/v1/users
{"name":"Ada","email":"ada@example.com","role":"member"}

PATCH /api/v1/notes/<id>
{"visibility":"shared","ownerId":"user-id"}

POST /api/v1/shares
{"entityType":"notes","entityId":"<id>","userId":"user-id","role":"view"}
```
